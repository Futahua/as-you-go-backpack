[2026-08-06 Asia/Saigon] BRAIN - CREATOR UX DIRECTION
SESSION-FIRST LIVE LAYOUTS, QUICK PICKING AND MEMBER OPERATIONS
======================================================================

This entry supersedes the earlier assumption that the ordinary use case is a
carefully named, manually captured static arrangement.

PLAIN MODEL
- A new layout is lightweight and session-first. The creator expects to make
  several rapidly, use them for roughly a session, then discard most of them.
- Ease of creating, filling, rearranging and deleting a layout is therefore
  more important than an elaborate preset editor.
- Layout deletion removes only the layout item and its membership/geometry. It
  NEVER closes member windows by default.
- A separate explicit, confirmed "close member windows" choice may exist. It
  acts only on windows resolved as members at that moment and fails closed on
  missing/ambiguous identity. Deleting and closing must not be conflated.
- If a layout proves useful, the creator can explicitly KEEP it. Do not solve
  the full kept-layout lifecycle in 009 or the first one-window slice.

LIVE STATE VERSUS PER-LAYOUT GEOMETRY
Every layout containing a window may display that window's current open/
minimized/maximized/missing state. Each layout nevertheless owns a DIFFERENT
saved bounds/state entry for that membership, so the same window may appear in
multiple layouts at different positions and sizes.

To prevent one physical move from silently overwriting every alternate layout,
only ONE layout is active/recording at a time:
- Creating or activating a session layout makes it the recording layout.
- While active, adding/removing members and moving/resizing member windows
  continuously updates that layout's current arrangement; there is no Save
  Positions ceremony for the ordinary session workflow.
- Inactive layouts still observe live status but retain their own geometry.
- Activating another layout applies its retained geometry, restores/opens the
  requested members, and transfers recording to that layout.
- Kept/frozen behavior will later add an explicit choice; do not let it muddy
  the live session proof. Persist live edits promptly for crash recovery, but
  do not invent automatic shutdown deletion before a creator-approved policy.

MEMBER PICKER
- A layout offers "Pick onscreen windows." The picker lists currently visible,
  eligible top-level windows with the program icon by default and enough title/
  application detail to distinguish them.
- Picking an absent member links it; picking an existing member again unlinks
  it. A layout contains a given resolved window identity at most once.
- The same window may be linked to many layouts. Runtime observation should be
  shared/deduplicated, while membership and geometry remain per-layout.
- Picker resolution fails closed on ambiguity and excludes Papers/internal,
  tool, invisible and unsafe system windows according to explicit rules.
- Manual member-button order is independent of desktop position and persists
  per layout. Reordering never changes window bounds.

MEMBER SELECTION AND ACTIONS
- Member selection lives INSIDE the layout item and is separate from ordinary
  workspace-item selection. A normal member click may retain the eventual
  minimize/restore toggle; Ctrl-click (or an equally clear tested affordance)
  toggles member multiselection without starting graph drag.
- Reorder is a deliberate member drag/handle interaction and must not move the
  outer workspace item. Background drag continues to move the layout item.
- Group actions apply to selected members when any are selected, otherwise to
  every member. Required actions: restore/open, minimize and isolate.
- Isolate means restore/open the selected members and minimize the UNSELECTED
  members OF THIS LAYOUT only. It never changes windows outside this layout.
- Opening a closed member requires safe stored launch identity; an already-open
  member is restored. Missing/ambiguous members remain reported, never guessed.
- Default member visuals use the owning program's icon; status is a small,
  static semantic indicator with no repeating animation.

ARCHITECTURE CONSEQUENCES
- Persist per-layout ordered memberships and per-membership geometry, not HWNDs.
- Keep live observations/runtime handles in one host-side registry so duplicate
  membership across layouts does not create duplicate polling/hooks.
- Maintain an explicit active-recording layout id separately from each layout's
  contents. Only that id is allowed to write movement/resizing observations back
  into geometry.
- UI updates patch member interiors/status and must not rebuild or reheat graph
  physics.
- 008's explicit Save Positions fixture control is no longer the primary flow.
  It may be removed or later repurposed for kept/frozen layouts; Proof C must
  not require it for an ordinary session layout.
